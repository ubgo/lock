# contrib/gocronlock — guide

> Adapter that turns any `ubgo/lock` backend into a
> `gocron.Locker`. Drop into `gocron.WithDistributedLocker(...)`
> for instant cron-singleton mode without per-job boilerplate.

## When to use gocronlock

**Pick gocronlock when:**

- You use `github.com/go-co-op/gocron/v2` for scheduling.
- You want to coordinate cron-job execution across replicas
  using any of the family backends.

**Don't pick gocronlock when:**

- You don't use gocron — call the family backend's `WithLock`
  directly per job.
- You only run one replica — gocron's local mutex is enough; no
  need for any distributed locker.

## Quickstart

```go
import (
    "github.com/go-co-op/gocron/v2"
    "github.com/redis/go-redis/v9"
    "github.com/ubgo/lock/contrib/gocronlock"
    "github.com/ubgo/lock/redislock"
)

func main() {
    rdb := redis.NewClient(&redis.Options{Addr: "redis:6379"})
    locks := redislock.NewFactory(rdb)

    scheduler, _ := gocron.NewScheduler(
        gocron.WithDistributedLocker(gocronlock.New(locks.AsLocker())),
    )
    scheduler.NewJob(
        gocron.DurationJob(time.Minute),
        gocron.NewTask(syncJob),
        gocron.WithName("sync-data"),  // ← lock name is the job name
    )
    scheduler.Start()
    select {} // run forever
}
```

gocron auto-locks each job by name on every tick. Only the replica
that wins the Acquire runs the job; others silently skip.

## Why a separate module

gocron pulls a heavy dep tree (cron parser, clockwork, uuid). Most
users of `ubgo/lock` aren't running gocron, so we don't pollute
their dep graph. The adapter lives in its own subpath at
`github.com/ubgo/lock/contrib/gocronlock`, with its own go.mod.
Users who don't import it never see gocron's deps.

## How it works

gocron's interface:

```go
// In gocron:
type Locker interface {
    Lock(ctx context.Context, key string) (Lock, error)
}
type Lock interface {
    Unlock(ctx context.Context) error
}
```

We wrap any `lock.Locker` to satisfy this:

1. `Lock(ctx, key)` calls `inner.Acquire(ctx, key)`. Returns a
   `gocron.Lock` adapter on success.
2. `Unlock(ctx)` calls the underlying `Holder.Release()`. (We
   ignore Unlock's ctx because `lock.Holder.Release()` doesn't
   take one; for distributed backends this means cleanup uses
   `context.Background()`.)
3. `gocron.ErrLocked`-equivalent — gocron treats any `Lock`
   error as "skip this run." We return the family's
   `lock.ErrLocked`, which gocron correctly skips.

## API reference

```go
import "github.com/ubgo/lock/contrib/gocronlock"

// One function, one signature:
gocronlock.New(l lock.Locker) gocron.Locker
```

That's the whole adapter. No options, no factory pattern — just a
function that wraps.

## Use cases

### 1. Cron-singleton across replicas, with Redis

```go
rdb := redis.NewClient(&redis.Options{Addr: cfg.RedisAddr})
locks := redislock.NewFactory(rdb, redislock.WithTTL(10*time.Minute))

scheduler, _ := gocron.NewScheduler(
    gocron.WithDistributedLocker(gocronlock.New(locks.AsLocker())),
)
scheduler.NewJob(
    gocron.CronJob("0 0 * * *", false),
    gocron.NewTask(processBilling),
    gocron.WithName("midnight-billing"),
)
```

Three replicas wake up at midnight; only one wins the Redis SET-NX,
the other two skip. No manual `WithLock` per job.

### 2. Postgres-backed cron-singleton

```go
locks := pglock.NewFactory(pool)
scheduler, _ := gocron.NewScheduler(
    gocron.WithDistributedLocker(gocronlock.New(locks.AsLocker())),
)
```

Cleanest crash-recovery story — Postgres releases the lock when
the holder's session disconnects. No TTL.

### 3. Single-host crons via flock

```go
locks := flock.NewFactory(flock.WithDir("/var/run/myservice"))
scheduler, _ := gocron.NewScheduler(
    gocron.WithDistributedLocker(gocronlock.New(locks.AsLocker())),
)
```

For services with a single replica that just want crash safety
without infra. The kernel handles cleanup.

### 4. Tests

```go
locks := memlock.NewFactory()
scheduler, _ := gocron.NewScheduler(
    gocron.WithDistributedLocker(gocronlock.New(locks.AsLocker())),
)
```

Test scheduling logic without spinning up Redis/etcd/Postgres.

## Operational notes

### Always set `gocron.WithName(...)`

gocron uses the job name (or function name if unnamed) as the
lock key. Anonymous functions get autogenerated names that are
NOT stable across builds. Two replicas with different builds
might use different lock names and both run the job.

**Always pass `gocron.WithName("...")`** when using gocronlock.

### Naming conflicts

If two different jobs share a name (or the autogenerated function
name happens to collide), they share a lock. Surprising! Use
explicit names with prefixes for safety:

```go
gocron.WithName("billing.midnight-export")
gocron.WithName("reports.midnight-export")
```

### TTL sizing for distributed backends

gocron acquires the lock at job start and releases at job end.
If you use `redislock` or `etcdlock`, the TTL must be longer
than the longest healthy run of the longest job — or the job
loses its lock mid-run. Auto-extend isn't wired through the
adapter. For long-running jobs, use the family backend's
`WithLock` directly instead of routing through gocron.

## Flaws

See [`docs/flaws.md` §contrib/gocronlock](../flaws.md#contribgocronlock):

- **gocron's `Locker.Unlock(ctx)` shape** — we ignore the ctx
  because the underlying `Holder.Release()` isn't ctx-aware.
- **Always set `gocron.WithName(...)`** — autogenerated names
  aren't build-stable.
- **Subpackage adds gocron's heavy dep tree** — by design.
